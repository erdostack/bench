# Graph decision

Decision: in-process-library

The question was whether the disruption desk, which from April covers the national network as well as its own, should keep the cut-off query as recursive SQL on the nightly SQLite export (Kofi: give the box more cores), move to a graph database (Ravi, earlier), or do something else. The recursive SQL no longer meets the need: on a merged test file it took 7.4 s p95 against the desk's 1 s (previously 120 ms p95), with the indexes on both section ends in place and the plan showing index lookups (all stated by the user). The edge set is about 389,800 sections, which fits in the memory of one process many times over, so the walk moves into memory; a graph database is not needed.

## Workload facts

- The question asked of the connections: from every core node, walk along track sections (both directions) skipping the closed section, then list stations with no reached node (sql/cut_off.sql). This is a reachability walk of data-dependent depth over the whole network, because it starts from all core nodes and so must reach every connected node.
- Walk form: the recursive CTE `reach(node_id)` carries only the node id and uses `UNION`, so a node reached again adds no row and loops end (sql/cut_off.sql). It is already the deduplicated form, so there is no one-row-per-route waste to remove. A correct answer has to visit every node reachable from the core, so the required work is the whole connected network: the walk's cost follows the size of the network, not the size of the closure.
- Size, now (from April, same nightly export): 2,600 national stations and 380,000 track sections added to ours (stated by the user). Merged: 640 + 2,600 = 3,240 stations and 9,800 + 380,000 = 389,800 track sections (derived; the 640 and 9,800 are the earlier figures, stated by the user and recorded here before this change). Network size grows by 389,800 / 9,800 = about 39.8 times. The number of track nodes is unknown; the walk is over track nodes, not stations (db/schema.sql).
- Measured latency, now: 7.4 s p95 on a merged test file, indexes on both section ends in place, plan showing index lookups (stated by the user, not re-measured here; no database copy in the repo, var/ and *.db are git-ignored). Before the merge: 120 ms p95 (stated by the user). 7.4 s / 0.12 s = about 62 times slower for about 39.8 times the sections, so the cost follows the network size, as the walk form above says.
- Latency requirement: the desk needs an answer within 1 s (stated by the user, earlier). 7.4 s is 7.4 times the limit (7.4 / 1). Before the merge 120 ms was 12% of it.
- Remedies already in place or ruled out: the indexes `section_a` and `section_b` exist and are used (stated by the user; db/schema.sql). More cores (Kofi's proposal) has not been run. It is the remedy for a query that is held up by several statements competing for the machine; here there is one statement running about every 16 minutes (see load), so there is nothing to spread over cores. No measurement shows that cores help one recursive walk, and the measured failure stays a failure until something is run.
- Load: about 30 closure look-ups a day (stated by the user, earlier; whether the April scope changes it is unknown); online lookups from the desk, effectively one at a time (30 a day is about one every 16 minutes over an 8-hour shift: 480 min / 30).
- Writes and freshness: the register export is rebuilt every night into `var/infra.db` (stated by the user; README.md). An answer may be up to a day old by design, so a structure loaded after each nightly rebuild meets the freshness required.
- What is operated today: one box with 8 GB, SQLite file (stated by the user; README.md). Number of processes serving the desk: unknown; `disruption/desk.py` is run as a command per look-up (disruption/desk.py).
- Memory for an in-process copy: measured on synthetic data of the same edge count, 389,800 edges between 300,000 nodes with one integer attribute per edge: NetworkX 3.7 on Python 3.13 used about 198 MB, about 507 bytes per edge (tracemalloc); a plain dict of adjacency lists used about 117 MB, about 300 bytes per edge. These are extrapolations from random data, not the real export. Against 8 GB, one copy is about 2.5% (198 MB / 8,192 MB), and even ten copies would be about 25%.
- What was already tried: unknown beyond the indexes above; the repo holds no decision records, migrations or bench notes.
- unknown: track node count (and so the real memory), and the maximum (not just p95) latency; whether the 30 look-ups a day rises with the national scope; how long it takes to build the structure from the nightly export at 389,800 sections, which depends on whether it is held in a long-running process or rebuilt for each look-up (a trial item, not a fact about today's workload); the real depth. Looked in README.md, db/schema.sql, sql/, disruption/.

## Options considered

- graph-database (a dedicated graph store, as Ravi proposed): rejected, because the edge set of about 389,800 sections fits in one process with room to spare (about 198 MB against 8 GB), it changes only with the nightly rebuild, and the load is about 30 look-ups a day, one at a time. A second stateful system and a feed from the nightly export would not buy anything the in-memory copy does not. It would not remove the walk across the whole network either.
- in-process-library (the edges loaded into memory, for example NetworkX or a plain adjacency structure): chosen, because recursive SQL is measured failing at 7.4 s p95 against 1 s on the merged data, the cost grows with network size, and the edges fit in memory (about 198 MB measured on synthetic data of the same count, one copy, 8 GB box), while a nightly reload meets the day-old freshness. Shape of the change, not applied here: load sections and core nodes from `var/infra.db` after each nightly rebuild into one long-running process (or a cached structure) so each look-up does not pay the load, then answer a closure by a breadth-first search from the core nodes that skips the closed section. The trial before committing: load the merged export, time the load and the search for a few dozen real closures, and check p95 against 1 s.
- recursive-sql (recursive queries on the SQLite file already run): rejected for now, because it is measured at 7.4 s p95 against the 1 s need on the merged file, with the indexes in place and index lookups in the plan, and the query is already the node-id-only `UNION` form. The walk has to cover the whole network on every call. More cores (Kofi) is not shown to help: it has not been run, and one statement runs at a time. Reopen only if something is run that brings it under 1 s p95 on the merged file.
- no-graph (plain joins, no traversal): rejected, because the question is reachability from the core over a path of unknown length, which needs a walk.

## What would change the decision

- A recursive query on the merged data, rewritten or on bigger hardware, measured at or under 1 s p95 on the real merged `var/infra.db` would move this back to recursive-sql, because the cheaper option would then be shown to meet the need.
- The in-process trial (load the merged export, then search a few dozen real closures) missing 1 s p95, or one copy of the structure measured above the box's memory (8 GB) once the real track node count is known, would reopen the question; the desk owner sets the latency budget.
- A requirement to answer many closures at once, or to run whole-network analysis such as every single-section closure in one batch, would strengthen in-process-library.
- Look-ups rising from about 30 a day to many a second, or the register changing continuously through the day instead of nightly, with the in-process structure measured failing, would be the conditions for reconsidering graph-database. Nothing in the request points there.
- A cycle or a disconnected piece in the national data does not change the option; the walk ends on seen nodes, and a node in no connected part of the core is reported as cut off.
