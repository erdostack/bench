# Graph decision

Decision: in-process-library

The question was where the permit diversion checker should keep the road network (a graph database, a library in the worker, recursive SQL, or no graph) once the supplier's regional extract was delivered. The check is a weighted shortest path, and the delivered extract (180,000 segments, 150,000 junctions) scales the pilot's measured 70 MB for 38,000 segments to about 332 MB, which is about 22% of the 1.5 GB worker limit and leaves room, so the library the prototype already uses holds. Earlier this record said need-more-information because the extract size was unknown; that fact is now known.

## Workload facts

- The question asked of the connections: the quickest diversion round a closed segment for a vehicle of a given weight, a weighted shortest path (Dijkstra, `nx.dijkstra_path` in roads/diversion.py) between the closed segment's end junctions, skipping the closed segment and any segment whose max_weight_t is below the vehicle weight. Data-dependent depth, and a path algorithm; not expressible as a lookup or a fixed number of joins (roads/diversion.py).
- Latency budget: a check has to come back within 2 s (stated by the user).
- Load: about 300 checks a day (stated by the user), roughly 1 every 4.8 minutes over 24 hours (86,400 s / 300 = 288 s; derived). Concurrency is very low; online request with a latency budget.
- Memory limit: hard 1.5 GB per worker on the permit platform (stated by the user). The number of workers each holding a copy is unknown; the limit is per worker.
- Pilot data: the county sample from the supplier, 38,000 segments (stated by the user). The prototype holds the network in about 70 MB and a route takes 30 ms (stated by the user; measured by them, the prototype is roads/diversion.py with networkx 3.7 per requirements.txt).
- Regional extract, delivered: 180,000 segments and 150,000 junctions (stated by the user). This replaces the earlier unknown. It is 180,000 / 38,000 = about 4.7 times the pilot's segments. The pilot's junction count was not given, so the junction-to-segment ratio of the sample is unknown.
- Memory per segment, derived: 70,000,000 B / 38,000 = about 1,842 B per segment (decimal MB; the prototype graph is a MultiDiGraph with two directed edges for each two-way segment, db/schema.sql has an `oneway` flag).
- Memory for the regional extract, derived: 180,000 x 1,842 B = about 331.6 MB, which is 331.6 / 1,500 = about 22% of the 1.5 GB limit (decimal; about 21% of 1,610,612,736 B). This assumes memory grows linearly with segments in the sample's shape and that the extract carries the same attributes as db/schema.sql; it is an extrapolation, not a measurement on the extract. Even if the real cost per segment were 3 times the sample's (about 1 GB), it would still be under the limit, though that leaves little room for the interpreter and service code. Nodes are counted inside the per-segment figure: if junctions cost more per segment than in the sample (150,000 junctions for 180,000 segments is a high ratio of junctions to segments, and the sample's ratio is unknown), the true figure is higher than 332 MB.
- Time on the extract, a first estimate only: if a check scaled with the whole network, 30 ms x (180,000 / 38,000) = about 142 ms, against the 2 s budget (derived, extrapolation). A diversion search explores the area around the closure, so this is an upper-end estimate. The 300 checks a day mean checks almost never overlap.
- Prototype inefficiency: `diversion()` finds the closed segment by scanning every edge (`g.edges(keys=True)`), and the weight function loops through parallel edges; that scan is linear in edges per call (about 2 x 180,000 directed edges at most), and an index from segment_id to its junctions removes it. It is waste in the check, not a reason for a different storage choice.
- Storage today: SQLite `var/roads.db`, not committed; the full extract replaces the county sample when delivered (README.md). Tables are junction (with x, y) and segment (db/schema.sql); there are no indexes on from_j and to_j, because the prototype loads everything.
- National product: about 4 million segments (stated by the user). 4,000,000 x 1,842 B = about 7.4 GB, about 4.9 times the 1.5 GB limit (derived), so the national extract would not fit in this prototype's structure. The regional extract is not the national one.
- unknown: how many worker processes per host would each hold a copy (the limit is per worker, so this does not change whether a copy fits), the load time of the extract at full size (the sample's load time was not given), and the supplier's refresh cadence (no freshness requirement is stated anywhere).
- unknown: segment attributes in the regional extract beyond those in the schema (geometry and names would add memory if loaded).
- Nothing was run: the database and the extract are not in the repo, so no row counts, timings or memory were taken here; the 70 MB, 30 ms, 180,000 and 150,000 are the user's figures.

## Options considered

- graph-database (a dedicated graph store, as Dan from the platform team proposes): rejected, because the regional network is about 332 MB in the existing structure, 22% of the 1.5 GB worker limit, and a route took 30 ms against a 2 s budget at 300 checks a day. It would add a stateful system and a feed from the supplier to solve a problem the numbers do not show.
- in-process-library (networkx in the worker, as the prototype does): chosen, because the extract fits (about 332 MB of 1.5 GB, derived from the 70 MB per 38,000 segments measured by the user) and the time estimate is about 142 ms at most against 2 s. Proposed changes (not made here): look up the closed segment's junctions through an index built at load time instead of scanning every edge, and measure resident memory and a route time on the delivered extract before release.
- recursive-sql (recursive queries on SQLite): rejected, because the question is a weighted shortest path with a vehicle weight limit; a recursive query would enumerate routes rather than run Dijkstra, which is the waste the heuristics warn about, and no measurement shows it meeting 2 s.
- no-graph (plain joins, no traversal): rejected, because the check is a shortest-path search of data-dependent depth over a network of the same kind of things (junctions and segments).

## What would change the decision

- Resident memory of a worker after `load(conn)` on the delivered extract (measure it, for example with `resource.getrusage` or `tracemalloc`) coming close to the 1.5 GB limit, or a route taking longer than 2 s on it, would move this to a leaner array-based library, a dedicated routing service, or graph-database, with a trial on the full extract and the real check mix as the gate.
- The product moving from the regional to the national network (about 4 million segments, about 7.4 GB in this structure, derived) would exceed the worker limit and move this to graph-database or a compact routing service; at roughly 800,000 segments the same arithmetic (1,500,000,000 / 1,842) reaches the limit, before counting the worker's own memory.
- The platform team lowering the worker memory limit below what the measured copy needs, or a requirement for the road network to update within minutes of a change (no such requirement is stated; the supplier's refresh cadence and the limit are theirs to set), would reopen the choice.
- The number of checks a day growing from 300 to a rate where checks run at once and the 2 s budget is missed, measured as the 95th percentile of check time, would move this to a design with a shared routing service.
