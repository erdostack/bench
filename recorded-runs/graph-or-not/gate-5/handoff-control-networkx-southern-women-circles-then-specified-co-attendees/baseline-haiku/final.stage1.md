Decision: in-process-library

Load the attendance list into memory once and walk it outward step by step. A graph library is a reasonable way to do that, and networkx is already in `requirements.txt`. Neo4j is not needed.

Why this is a traversal:
- The "circles" page is a breadth-first walk. Step 1 is the women who attended an event with her. Step 2 is the women who share an event with someone in step 1, and so on until the whole network is covered. A walk like that is a graph problem, so "no graph at all" does not fit.

Why not a graph database:
- The network is 18 women, 14 events and 89 attendance rows, and it will never change. The whole thing fits in a few kilobytes of memory and is read on a shared host a few dozen times a week. A Neo4j server would add far more to run and keep alive than the problem warrants, and it would sit outside the stdlib-plus-networkx setup this repo already has.

Why not recursive SQL:
- The repo has no database today, only a CSV. Recursive SQL would mean creating and shipping a database file just to hold 89 rows. In-memory traversal reads the CSV directly.

What I checked, on the CSV in the working directory with a plain-Python breadth-first walk over an in-memory dictionary (not part of the repo):
- The file has 89 rows, 18 women and 14 events, matching the study figures.
- Every woman reaches all 18 women in the network. The farthest any woman is from the rest is 2 steps. Eleven women need 2 steps to reach everyone, and the other seven need only 1.

So the "step by step out to the whole network" view has at most two rings. That is a small page to build, and a plain walk over the in-memory data is enough. networkx would also work, and it is a fine choice if the page later needs its shortest-path helpers.

Notes:
- `README.md` says `data/attendance.csv` is generated by `setup.py` from the copy bundled with networkx, but there is no `setup.py` in this directory. The CSV is the data the pages read, so the provenance note should be fixed or the script added before the exhibit.
